# Hive System Redesign — Proposal

A redesign of the AVP-Alien hive system that leans on BLib's faction *and*
territory systems, splits "hive" into two distinct concepts, and is built to
scale beyond what tickable-entity counts allow.

This document is design-only. No code changes are proposed yet — only data
shapes, lifecycles, and decisions to make. An implementation outline is at the
end.

---

## 1. Vocabulary

The word **hive** is overloaded in the current system. The redesign separates
it cleanly.

| Term                  | Meaning                                                                          |
|-----------------------|----------------------------------------------------------------------------------|
| **Hive Faction**      | A `Faction<HiveFactionData>` in BLib. The *who* — the political collective that owns members and claims. Variant-locked. May contain many Hive Locations. |
| **Hive Location**     | A fixed `BlockPos` in a single dimension that anchors a contiguous claim of chunks. The *where*. Belongs to exactly one Hive Faction. Owns reserves, leadership, and a boss bar. |
| **Variant Pool**      | A per-dimension, per-variant global reserve of *shed* aliens. Shared across all Hive Factions of that variant. Used to feed locations that summon reinforcements. |
| **Forager**           | An alien with no Hive Faction membership. A pre-state for joining or being shed. |
| **Biomass**           | The internal resource that powers territory expansion. Generated by hive activity, consumed by claims. Per-location. |

The everyday metaphor: think *village*. The plot of land where the
houses cluster is the **village** (the location). The villagers who live
there are the **village's faction**. A villager who walks to another village
is part of *that* village's faction now, but the *original village location*
is unchanged. Two villages can belong to the same kingdom (faction); a
kingdom is many villages plus its citizens.

## 2. Constraints satisfied

| # | Constraint                                                                  | Where it lives in this design                              |
|---|-----------------------------------------------------------------------------|------------------------------------------------------------|
| 1 | Hive = faction + location, not one merged thing                             | §1, §3                                                     |
| 2 | Locations have a fixed center                                                | §3.2                                                       |
| 3 | Boss bar tied to location, distance-gated                                    | §6                                                         |
| 4 | Territory growth that gets more expensive but can be sustained               | §5 (biomass + claim cost curve)                            |
| 5 | Hive always has a leader (some kind of xenomorph)                            | §7                                                         |
| 6 | Numbers must scale beyond tickable-entity counts (reserves)                  | §4 (location-local + variant pool)                         |
| 7 | Members shed to a global pool when they wander, not for young hives          | §4.4                                                       |
| 8 | Variant-aware, mutually exclusive                                            | §3.1                                                       |
| 9 | Reserves localized to locations, not shared across distant locations         | §4.1                                                       |

## 3. Data model

### 3.1 Hive Faction

A standard BLib `Faction<HiveFactionData>` keyed by a fresh `ResourceLocation`
(retained pattern: `avp_alien:hive/<UUID>`).

`HiveFactionData` fields:

```
HiveFactionData
  variant: AlienVariant                  // immutable. NORMAL, ABERRANT, NETHER, IRRADIATED.
  locationIds: Set<HiveLocationId>       // back-reference to owned locations
  ageInTicks: int
  removalReason: HiveRemovalReason | null
  // No center pos — locations carry that.
  // No reserves — locations carry those.
  // No leadership — locations carry that.
  // No boss bar — locations carry that.
```

**Variant rule.** A faction's variant is fixed at creation. An alien whose
variant differs from the faction's variant cannot be a member. If an alien
mutates mid-membership (e.g. becomes irradiated), the faction's `onMemberLoaded`
detects the mismatch and ejects the alien to forager state. (Same hook BLib
already gives us.)

**Variants are mutually exclusive.** Four hive factions max per "lineage."
Two factions with the same variant *can* coexist (e.g. two queens on opposite
sides of the world founded separate empires) — they share the global Variant
Pool but not membership.

`HiveRemovalReason` is converted from an enum to a sealed interface with
record subtypes (matches the project's convention against enums for
extensible types):

```java
sealed interface HiveRemovalReason {
    record NoLocationsRemain() implements HiveRemovalReason {}
    record AbsorbedBy(ResourceLocation absorberFactionId) implements HiveRemovalReason {}
    record AdminRemoved(String reason) implements HiveRemovalReason {}
}
```

### 3.2 Hive Location

A persisted, per-faction structure:

```
HiveLocation
  id: HiveLocationId                    // typed wrapper around UUID
  factionId: ResourceLocation           // owning HiveFaction
  dimension: ResourceKey<Level>
  centerPos: BlockPos                   // FIXED — never moves after creation
  ageInTicks: int
  founderId: UUID                       // queen that founded it
  leadershipManager: HiveLocationLeadership
  reserveManager: HiveLocationReserves
  bossBarManager: HiveLocationBossBar
  biomass: int                          // currency for expansion (see §5)
  claimedChunks: Set<ChunkPos>          // mirror of BLib territory claims for THIS location
  removalReason: HiveLocationRemovalReason | null
```

**Center is fixed.** Set at creation, never updated. Solves the old system's
"hive shifts under players' feet" problem (`§9.3.11` of the analysis doc).
The founding queen can roam; the location stays put.

Hive locations are stored in a registry keyed by `HiveLocationId`. The
registry has dimension-keyed indexes (chunk-pos → location, and faction-id →
locations) for O(1) lookups.

```
HiveLocationRegistry (server-global, like HiveRegistry today)
  byId:        Map<HiveLocationId, HiveLocation>
  byFaction:   Map<ResourceLocation, Set<HiveLocationId>>
  byChunk:     Map<ResourceKey<Level>, Map<ChunkPos, HiveLocationId>>
  byCenterDim: Map<ResourceKey<Level>, SpatialIndex<HiveLocation>>  // bucketed grid for nearest-by-pos lookups
```

The `byChunk` map is critical: it makes "which location owns this chunk"
O(1), which BLib's territory store can't tell us alone (BLib only knows
faction). It's persisted alongside the location records.

### 3.3 Variant Pool

Per-level saved data, one record per variant:

```
VariantPool
  dimension: ResourceKey<Level>
  poolsByVariant: Map<AlienVariant, EntityReserves>
```

Entries live on `ServerLevel` save data (one `VariantPool` per dimension, with
sub-pools per variant). Aliens shed from a hive go *here*. Locations may
*draw from here* during summoning (constraint §4.5).

### 3.4 Foragers

Foragers (aliens without a hive) carry no special data — they're aliens
whose `HiveManager` resolves to `Option.none`. The variant pool is *not*
membership; foragers are plain world entities. The pool is purely a counter.

## 4. Reserves

### 4.1 Local reserves (per location)

Each `HiveLocation` keeps an `EntityReserves` (BLib's existing multiset).
When a `HiveLocation` spawns members, it draws from its own reserves only.
Reserves never automatically transfer to other locations. This satisfies
constraint #9.

### 4.2 Sources of local reserves

| Source                                                           | Effect                                              |
|------------------------------------------------------------------|-----------------------------------------------------|
| Aliens within the location's territory kill non-aliens           | +1 (or +genes-bonus) of caste's drone/runner/burster |
| Aliens within the location's territory despawn (chunk unload)    | +1 of own type — turning unloaded mass into reserves |
| Outer-edge xenomorphs idle for ≥ N seconds in the location's outer-ring chunks | +N drones/runners/bursters every M minutes (replaces the current "every 5 min" tick, scoped to the location) |
| Reinforcement summon from Variant Pool (§4.5)                    | +1 of caste type, drained from pool                 |

### 4.3 Spawn gating

A location is allowed to spawn natural mob aliens only:

- Within its claimed chunks,
- When `reserves.canSpawn(entityType)` is true,
- And the position satisfies the per-caste *layer-by-distance* rule (§5.3).

Each successful spawn decrements the location's reserve count for that type.

This preserves the old system's "reserve-bounded spawning" behavior, just
local to a location.

### 4.4 Shedding (member → Variant Pool)

An alien becomes a candidate for shedding when *all* of these are true:

- The alien is a member of a Hive Faction,
- The alien is **outside** every claimed chunk of every location of its
  faction (in any dimension), continuously for at least `SHED_GRACE_TICKS`
  (default 5 minutes),
- The faction has at least `MIN_FACTION_AGE_FOR_SHEDDING` total age
  (default 30 minutes — protects young hives from bleeding members),
- The faction owns at least `MIN_LOCATIONS_FOR_SHEDDING` locations
  (default 1 — would only matter if you allow factions with zero
  locations as a transient state),
- The alien is alive (not being killed; killed members are removed normally).

When all conditions are met:

1. The alien is removed from the faction's membership.
2. The alien's entity type is added (1 count) to the appropriate
   `VariantPool` entry for its dimension and variant.
3. The alien itself remains in the world, now a forager. Its `HiveManager`
   becomes `Option.none`. It can re-attach to any same-variant location
   later.

This satisfies constraint #7 and is the bidirectional partner to §4.5.

### 4.5 Reinforcement (Variant Pool → location)

Locations actively pull from their dimension's `VariantPool` entry for their
variant when:

- A `cryForHelp` event fires from one of their xenomorphs,
- AND the location's local reserves cannot satisfy the summon,
- AND the variant pool has the requested type available,
- AND the summon target is a vent inside the location's territory.

Effect:

1. Decrement the variant pool by 1 of the requested type.
2. Increment the location's local reserves by 1 (a logical transfer).
3. The vent spawns immediately as today.

This makes shedding economically meaningful: aliens that drift away
"return home" through the pool when the location calls for them. From a
player's perspective, a shed alien isn't "gone" — it's a chip in a pool
the species draws from when pressed.

It also keeps the count realistic: the global pool can't exceed
"aliens that have actually been shed minus aliens that have been
re-summoned." No magic conjuring.

### 4.6 Soft caps

`EntityReserves` is unbounded. We add per-type soft caps tied to
location size:

```
maxReservesForType(loc, type) =
    BASE_CAP_FOR_TYPE
  + CAP_PER_CLAIMED_CHUNK_FOR_TYPE * loc.claimedChunks.size()
```

If a source would push reserves over the cap, the excess spills to the
variant pool. (A bursting hive's surplus goes to the species, not lost.)

The variant pool also has a per-type cap to prevent runaway storage on
servers that never draw from it; the same spillover logic applies, but
spilled-from-pool counts are simply discarded.

## 5. Territory & growth

### 5.1 The expansion loop

The hive grows by claiming new chunks via BLib's `TerritoryManager`. The
mod-side `HiveLocation` records the claim under its `claimedChunks` set
and updates the `byChunk` index.

A `HiveLocation` may claim a `ChunkPos` only if:

1. **Adjacency.** The chunk is cardinally adjacent to a chunk already
   claimed by *this same location*. (The founding queen's chunk is the
   first claim; growth radiates from there.)
2. **No same-variant overlap.** The chunk is not already claimed by a
   different `HiveLocation` of *the same variant*. (Different-variant
   factions may contest — see §5.2.)
3. **Biomass cost paid.** The location has enough biomass to spend
   (§5.4).
4. **Cooldown elapsed.** A per-location claim cooldown has elapsed
   (default 30 seconds) to keep growth from happening in bursts and to
   give the server room to breathe.
5. **Activity gate.** A xenomorph member of the location stood in the
   target chunk within the last `CLAIM_ACTIVITY_WINDOW` ticks. *No
   activity, no claim.* This forces growth to be earned — the hive
   spreads where its members have actually been.

When all are met, the location:

- Spends biomass,
- Calls `Alien.MOD.territories().addClaim(level, pos, factionId)`,
- Adds the chunk to its `claimedChunks`,
- Updates `byChunk` index.

### 5.2 Contested chunks

If a different-variant location's territory borders the target chunk,
both locations may claim it simultaneously. BLib supports
multiple claimants — `isContested` returns true. While contested, neither
side's normal claim benefits apply; the chunk ticks faster on the
location whose members actually occupy it (resolution rule below).

**Contest resolution.** Every `CONTEST_TICK_WINDOW` (default 60 seconds),
each contested chunk evaluates: which contesting location has more
xenomorph members within the chunk? The losing location's claim is
*removed* from BLib for that chunk. If it was the only claim still
contesting, the winner becomes the sole claimant.

### 5.3 Caste distance rule

The old system's percentile-based sphere layers are replaced with a
straight-line distance from the location's center, expressed in chunks:

| Caste                      | Allowed distance (chunks from center) |
|----------------------------|--------------------------------------|
| Queen                      | 0 (center chunk only)                |
| Praetorian / Crusher       | 0–2                                  |
| Drone / Runner / Ovomorph  | 0–6                                  |
| Warrior / Prowler          | 2–10                                 |

These thresholds are config (`AlienProperties.Hive.*_RANGE_CHUNKS`).
Crucially, distance is to the *fixed center* — moving the hive is no
longer a thing.

A spawn is only valid in a chunk that:
- The location *claims*,
- And whose distance from `centerPos.chunkPos` matches the caste's
  allowed range.

This gives shape (warriors patrol the edge, queens near the center)
without the old fragile percentile sphere.

### 5.4 Biomass — the growth resource

Biomass is the currency a location spends to claim chunks. It's
generated by hive activity inside claimed chunks, so a healthy hive
*can keep growing*; a starved hive *cannot*.

Sources of biomass (per location, per second):

| Source                                                                  | Biomass             |
|-------------------------------------------------------------------------|---------------------|
| Each loaded xenomorph standing in a claimed chunk                        | +1                  |
| Each kill of a non-alien mob inside claimed chunks                       | +25                 |
| Each successful resin block placed in a claimed chunk by a member       | +5                  |
| Each ovomorph existing inside claimed chunks                             | +0.5                |
| Idle bonus (location is non-angry and chunk-loaded)                      | +N flat (small)     |

Biomass is consumed only by claim attempts:

```
claimCost(loc, targetChunk) =
    BASE_CHUNK_COST
  * (1 + loc.claimedChunks.size() * GROWTH_FACTOR)
```

With `BASE_CHUNK_COST = 100` and `GROWTH_FACTOR = 0.05`, the first
chunk costs 100, the tenth costs 150, the fiftieth costs 350, the
hundredth costs 600. The cost is super-linear but not exponential —
the hive *can* outpace it as long as its membership keeps producing
biomass roughly proportionally to its size.

This satisfies constraint #4: growth gets more expensive, but if the
hive's biomass production scales with its membership (and membership
scales with territory because the caste rule lets bigger territories
host more aliens), the hive keeps up. There is no theoretical cap. A
20-member hive that starves can't grow; a 200-member hive that's
actively hunting can claim chunks faster than it loses them.

### 5.5 Territory shrinkage

Territory shrinks when:

- All members are removed from the faction (the faction enters death
  spiral — see §8.4).
- The location's biomass production is below maintenance for `T`
  consecutive minutes — claims at the *farthest* radius are released
  one per minute. ("The hive can't sustain its borders.")
- A contested chunk loses its contest (claim transferred or removed
  via §5.2).
- An admin command forces it.

The "release outermost first" rule maintains the visual shape of the
hive contracting toward its queen. This was already in the
`HIVE_TERRITORY_DESIGN.md` doc as a goal.

### 5.6 No more "leash sphere"

Membership is no longer distance-gated. An alien is a member of a
faction until it's *killed* or *shed* (§4.4). Aliens may freely roam
inside their faction's territory across multiple locations. The
shedding rule is the only mechanism for involuntary removal, and it's
slow (5-minute grace) and gated on faction maturity.

## 6. Boss bar

One `ServerBossEvent` per `HiveLocation`. Constraint #3 explicitly:
the bar is the *location's* bar.

### 6.1 Visibility (player → bar attachment)

A player is added to a location's boss bar when:

1. The player is in the same dimension as the location, AND
2. The player is within `BOSS_BAR_DISPLAY_RADIUS_BLOCKS` (default 96
   blocks) of the location's center, AND
3. The player is a valid target for the location's variant
   (`AlienPredicates.isValidTarget(variant, player)`).

This is purely *distance from center* — no need to be inside claimed
chunks. A player approaching the location sees the bar before they
hit any aliens, which gives a clear "you are entering hive territory"
moment.

### 6.2 Removal

A player is removed when:

- They leave the radius,
- They change dimension,
- They become an invalid target,
- The location dies.

Re-evaluation runs every 20 ticks (matches today's cadence).

### 6.3 Progress (xenomorph count)

The progress is *relative to the location only*:

```
loaded = location.factionData.getLoadedMembersByType()
  filter (uuid -> location.byChunk contains entity's current chunk)

reserves = location.localReserves.getCountMatching(XENOMORPHS)

progress = (loaded.count(XENOMORPHS) + reserves) / location.peakXenomorphCount
```

**Important:** `loaded.count` here filters to entities physically inside
this location's claimed chunks. An alien that's a member of the
faction but currently in another location's territory is *not* counted
on this bar. This satisfies the constraint that the boss bar is
"relative" to the location.

`peakXenomorphCount` decays slowly (1 per minute) so a softened-up
hive that recovers eventually shows a full bar again. (Fixes the old
system's `maximumSeenXenomorphCount` only-grows bug.)

### 6.4 "Angry" state

Same idea as today: a location is `isAngry()` if its bar has at least
one player. Angry locations:

- Don't claim new chunks (claim attempts pause),
- Don't release outermost chunks (no shrinkage during a raid),
- Don't shed members (a player attack shouldn't accelerate shedding),
- Aliens within the location are persistence-required.

When the last player leaves the radius and `ANGRY_GRACE_TICKS`
elapses, the location returns to peaceful state.

## 7. Leadership

Constraint #5: hive always has a leader, must be a xenomorph.

### 7.1 Per-location leadership

Every `HiveLocation` runs `PickBestLeaderTask` independently. The
disposition table from `HiveLeaderDispositionUtil` is reused
(Queen=4 … Drone=0). Leader is the highest-disposition loaded
xenomorph **inside the location's claimed chunks**.

**Crucial change:** the leader lookup is restricted to xenomorphs
*physically present* in the location's territory. This prevents the
queen of location A from being miscounted as the leader of location B
just because both belong to the same faction.

### 7.2 Vacancy

If no xenomorph is in the location's territory, the location enters a
**Dormant** state:

- No claim attempts,
- No spawning (reserves are frozen, not lost),
- No leader,
- Boss bar progress reads zero,
- The location is *not dead* — eggs and facehuggers in the territory
  keep the location alive (see §8.3).

When a xenomorph re-enters the territory, the location wakes up,
PickBestLeader runs on its next cadence, and normal operation
resumes.

This means the constraint "a hive has a leader at all times" is
relaxed slightly: a *living* location has a leader whenever it has
any xenomorphs. A dormant location is "in stasis" — not failing the
constraint, but waiting.

### 7.3 Faction-level "Matriarch"

Optional (open question): a per-faction *Matriarch* — the
highest-ranked queen across all locations, chosen by the faction.
She has no per-tick effect; she's a target for storytelling and
advancement triggers ("Slay the Matriarch of the Aberrant strain").
If we add this, it lives on `HiveFactionData` and updates when any
location's leader changes.

## 8. Lifecycles

### 8.1 Faction creation

A new `HiveFaction` is created when:

- A queen of variant V spawns naturally (or via a queen-spawn-egg)
  AND no `HiveFaction` of variant V already exists in this dimension's
  region (configurable distance from any existing variant-V faction's
  centers).

The faction is variant-locked at creation. The creating queen also
founds her first `HiveLocation` (§8.2).

There is no "non-queen creates a faction" path. A non-queen
xenomorph that finds itself without a faction stays a forager
until either (a) it finds a same-variant faction's territory and
joins it, or (b) it dies or despawns (becoming variant pool stock
just like any forager would).

### 8.2 Location creation

A new `HiveLocation` is created when:

- A queen of a faction's variant settles at a position that is
  outside every existing same-variant location's claimed territory
  AND meets a "settlement validity" check (e.g. solid ground, near a
  resin-replaceable surface, optional Y-level constraint), AND
- The faction either exists (queen joins it) or doesn't (queen founds
  it per §8.1).

The queen "settling" is a deliberate AI action — laying her first
ovipositor or staying in one chunk for `SETTLEMENT_TICKS` (default 60
seconds) without combat. This makes location founding a deliberate,
visible event rather than a side effect of spawning.

Effect:

1. Mint a `HiveLocationId`.
2. Set `centerPos` to the queen's chunk center.
3. Initial claim: the center chunk only.
4. Insert into the registry's three indexes.
5. Initial reserves: a small bootstrap budget (1 drone, 1 runner).
6. Initial biomass: 0.

### 8.3 Location death

A location dies when *all* of:

- It has zero claimed chunks (territory fully released), OR
- It is dormant (no xenomorphs in territory) AND has zero ovomorphs
  in territory AND has been dormant ≥ `LOCATION_DECAY_TICKS`
  (default 24 hours of game time).

On death:

- All remaining members in the location's territory are released to
  forager state (NOT killed) — they may re-attach to other locations.
- BLib claims for this location are released.
- The location's reserves spill to the variant pool, capped (§4.6).
- The location is removed from the registry.
- Players within the boss-bar radius receive an advancement (similar
  to today's `KILL_A_HIVE`, but renamed
  `DESTROY_A_HIVE_LOCATION`). Advancements only fire when the
  removal reason is "killed" — explicit eradication, not natural
  decay.
- The faction's `locationIds` set drops the id. If the faction now
  has zero locations, the faction enters its own death check (§8.4).

Note the deliberate split: an old hive with eggs left is no longer
auto-deleted. The eggs hatch, produce facehuggers, then xenomorphs,
and the location wakes up. This fixes flaw #3 of the old system.

### 8.4 Faction death

A `HiveFaction` dies when *all* of:

- It has zero locations, AND
- It has zero living members, AND
- The condition has held for `FACTION_DECAY_TICKS` (default 1 hour).

On death:

- BLib `Alien.MOD.factions().remove(factionId)` is called.
- BLib `BLibFactionRemoveEvent` fires; AVP-Alien's listener cleans up
  any stragglers.
- Variant Pool entries persist.

### 8.5 Faction merging (optional)

If the design includes it: two factions of the same variant whose
territories become adjacent (a chunk of A is cardinally adjacent to a
chunk of B) may merge after a cooldown. The "stronger" faction
absorbs the weaker. This is a knob to keep, since it preserves
behavior players may already expect.

If we drop merging entirely, that's also fine — same-variant
factions can simply contest each other forever, which is more
interesting for player-driven factional stories.

I'd recommend *keeping* an explicit merge but making it require
both factions to be *non-angry* and *adjacent for >5 minutes*. This
preserves the old system's intent without the silent "two hives
merge while you're not looking" behavior that surprises players.

## 9. Validity & sanity rules

These are global predicates that maintain consistency:

| Rule                                                                                       | Enforced by                     |
|--------------------------------------------------------------------------------------------|--------------------------------- |
| Faction has exactly one variant, set at creation, never changed                            | `HiveFactionData` constructor    |
| All faction members have matching variant                                                  | `onMemberAdded` validates       |
| `byChunk` map is one-to-one with `HiveLocation.claimedChunks`                              | invariant; CRC checked at load   |
| Every location's `factionId` resolves to an existing faction                                | invariant; orphan locations are scrubbed at startup |
| Every chunk in a location's `claimedChunks` is claimed by the location's faction in BLib    | invariant; sync at startup       |
| A chunk in `byChunk[level][pos]` is claimed by exactly one location of any given faction   | enforced by `addClaim`           |
| Variant Pool counts are non-negative                                                       | `EntityReserves` already does this |

A `HiveLocationRegistry.validate()` runs at server start and logs (not
crashes) any inconsistency, attempting repair where possible.

## 10. BLib integration map

What BLib provides → how the redesign uses it.

| BLib concept                                     | Use in redesign                                                          |
|--------------------------------------------------|--------------------------------------------------------------------------|
| `Faction<T>`                                     | One per HiveFaction. Holds membership, mod data, sharded persistence.   |
| `FactionDataType<HiveFactionData>`               | Registered as `avp_alien:hive` (already exists).                         |
| `FactionMembership`                              | Source of truth for "alien is in faction." Drives shedding rule.         |
| `onMemberAdded(member, entity)`                  | Validate variant; reject if mismatched. Track typed bucket.              |
| `onMemberLoaded` / `onMemberUnloaded`            | Maintain `loadedMembersByType` per location.                             |
| `BLibFactionRemoveEvent`                         | Defensive cleanup of stale references.                                   |
| `TerritoryManager.addClaim`                      | Used by location growth (§5.1).                                          |
| `TerritoryManager.removeClaim`                   | Used by shrinkage (§5.5) and contest loss (§5.2).                        |
| `TerritoryManager.transferClaim`                 | Used by faction merge (§8.5) and contest resolution (§5.2).              |
| `TerritoryManager.isContested`                   | Used by `MaintainContestsTask` in the location's task list.              |
| `TerritoryManager.getAdjacentClaimedChunks`      | Used in claim adjacency check.                                           |
| `TerritoryManager.getChunks(level, factionId)`   | NOT used directly — we want per-location, not per-faction. Mod's `byChunk` is the source of truth. |
| Faction `name` / `color`                         | Optional: set the faction's name to e.g. "Aberrant Strain (Lineage of <queen-uuid>)" and pick a stable color. Improves any debug UI. |
| `RelationshipState`                              | Optional: same-variant factions default `NEUTRAL`; different-variant factions default `HOSTILE`. Drives an alien-on-alien combat predicate that's currently hand-rolled. |
| `ProtectionMode` (block break, etc.)              | Could mark hive territory as `OWN_FACTION_ONLY` for block break, granting the hive's chunks a soft "no griefing" semantic for non-aliens. Probably not for v1. |

What BLib doesn't provide but we need:

- A spatial index keyed by location *center* for "nearest location"
  queries (the mod owns this).
- A per-(level, factionId, location-id) index of which chunks belong
  to which *location* (BLib only knows faction-level).

## 11. Reserve / pool flow at a glance

```
                          ┌────────────────────┐
                          │   Variant Pool     │
                          │ (per-dim, per-var) │
                          └────────────────────┘
                            │             ▲
              §4.5 summon   │             │   §4.4 shedding
              (pool ↓ 1)    │             │   (pool ↑ 1)
                            ▼             │
                ┌─────────────────────────────────────┐
                │       HiveLocation reserves          │
                │       (per location, per type)       │
                └─────────────────────────────────────┘
                  ▲                 │
                  │   spawn         │   spawn (reserves ↓ 1, world entity ↑ 1)
   reserves ↑ 1   │                 ▼
                  │       ┌──────────────────────────┐
   §4.2 sources ──┘       │   World — loaded aliens  │
                          └──────────────────────────┘
                                      │
                            §4.6 spillover (overflow → pool)
                                      ▼
                          ┌────────────────────┐
                          │   Variant Pool     │
                          └────────────────────┘
```

Every transition is a single +1/-1 — no magic. The pool is the
buffer that makes population scale beyond loaded entities; the local
reserves are the buffer that makes spawn dynamics natural and
location-scoped.

## 14. Open questions

These are decisions worth resolving *before* code lands.

1. **Variant scope of factions.** One faction per variant per server, or
   one faction per *lineage* (queen-founded, allows multiple
   same-variant factions)? Recommendation: lineage. It's more
   interesting and supports stories like "two queens are at war."
2. **Cross-dimension factions.** Can a faction span multiple dimensions
   (overworld + nether locations under one queen)? Recommendation:
   no — variants tend to be biome/dimension-bound. Each faction is
   single-dimension; nether-variant factions only exist in nether.
3. **Forager attachment policy.** When does a forager re-join? On
   entering a same-variant location's territory? Or only on
   triggering a `requestToJoin`? Recommendation: on entering — keeps
   the player-visible behavior simple ("xenomorph wandered into the
   nest, became part of it").
4. **Variant Pool decay.** Should pooled counts decay over time?
   Recommendation: yes, at a slow rate (e.g. 1% per real-world
   day) to prevent infinite buildup on idle worlds. Pool is a
   buffer, not a savings account.
5. **Player factions.** BLib supports player-faction membership.
   Should players ever be able to "join" a hive (e.g. via a
   compatibility item from AVP-Predator)? Out of scope for v1
   but the design doesn't preclude it.
6. **Ovipositor/queen presence at location center.** Is the queen
   *required* to stay near the center for the location to grow?
   Recommendation: no — the queen wanders, but if she dies and no
   replacement exists, biomass production drops (handled naturally
   by membership reduction).
7. **Faction merging on/off.** §8.5 — keep, drop, or make a config
   knob? Recommendation: keep, gated more strictly than today.
8. **Migration from existing saves.** Convert each old `Hive` to one
   `HiveLocation` of a per-variant per-dimension `HiveFaction`,
   with the old center becoming the new (now-fixed) center, claiming
   the chunks within the old radius? Or hard reset on load?
   Recommendation: explicit migration, not reset — players will have
   established hives.

## 15. Implementation outline (high-level)

A rough order of work, with no estimates.

1. **`HiveLocation` and registry** — types, persistence, indexes.
   No behavior yet, just the data plumbing.
2. **`HiveFactionData` rewrite** — variant lock, location set,
   removal-reason sealed interface, validation in `onMemberAdded`.
3. **`HiveLocationRegistry.tick`** — replaces `HiveRegistry.tick`.
   Per-location `tick()` calls.
4. **Boss bar** — `HiveLocationBossBar` with distance-radius
   visibility (§6).
5. **Leadership** — `HiveLocationLeadership` per location, scoped
   to xenomorphs in claimed chunks.
6. **Local reserves** — port `HiveReserveManager` to per-location.
7. **Variant Pool** — new `VariantPool` saved data per dimension,
   shedding hook in `Alien.tick`, summon hook in `CryForHelpListener`.
8. **Territory expansion** — biomass tracking, claim cost curve,
   activity-gated claim attempts as a new `HiveLocationTask`.
9. **Caste distance rule** — replaces `HiveSpaceManager` in
   `AlienSpawning`, `EggLayingSensors`, `ResinManager`,
   `QueenSpawning`, `ResinVentBlockEntity`, etc.
10. **Contest resolution** — new task scanning
    `getAllContestedChunks` for chunks involving our factions.
11. **Founding** — queen settlement detection, location founding,
    faction founding when no same-variant faction exists.
12. **Death paths** — location dormancy, location death, faction
    death.
13. **Migration** — one-shot converter for old hive data on first
    load of a new-system world.
14. **Cleanup** — delete `HiveSpaceManager`, `MergeWithNearbyHiveTask`,
    `Hive`, `HiveRegistry`, all the moving-center logic. Keep
    `HiveIds`, `HiveLeaderDispositionUtil`, `HiveVentManager`,
    `HiveBossBarManager` (refactored).

Each step is separately mergeable as long as the old system still
runs alongside (feature flag the new one). Hard cutover happens at
step 14.

## 16. Summary

A hive becomes two cooperating pieces: a **Hive Faction** (variant-locked
political collective, owning members) and one or more **Hive Locations**
(fixed centers that own territory, reserves, leadership, and boss bars).
BLib's faction system holds the membership and persistence; BLib's
territory system holds the chunk claims. The mod adds the per-location
indexing that BLib doesn't provide on its own.

Growth is paid for in **biomass**, generated by hive activity inside
claimed chunks and consumed by claim attempts whose cost grows with hive
size. The hive can grow without bound *if* it can sustain biomass
production proportional to its territory; if it can't, it shrinks at the
edges first.

Population scales beyond Minecraft's tickable-entity limit through a
two-tier reserve system: **per-location reserves** for that location's
spawning needs, and a **per-dimension, per-variant pool** that holds
shed members and feeds reinforcements back. Aliens that wander too far
from their faction's territory are slowly shed into the pool; locations
under attack pull from the pool to summon. No magic — every count is a
+1/-1 of an entity that existed.

Boss bars belong to **locations**, are visible by **distance from the
location's center**, and count only xenomorphs in **that** location's
territory. The leader of each location is picked from xenomorphs
physically present in its territory, satisfying "always have a leader"
as long as the location isn't dormant.

Most of the old system's flaws are fixed structurally rather than
patched: the moving center disappears, the hive-with-eggs-dies bug
disappears, the spatial model becomes the same chunk-claim system the
rest of BLib speaks, and the linear scans become indexed lookups.
